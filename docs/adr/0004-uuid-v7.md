# ADR 0004 — UUID v7 comme clé primaire : migration à venir

- Statut : proposé (à faire dans une version dédiée)
- Date : 2026-11-10
- Règle concernée : guidelines « Identifiants » (UUID v7 pour toute entité exposée par l’API)

## Contexte

Les 15 entités utilisent des entiers auto-incrémentés, visibles dans l’API et dans les adresses de
l’application (`famille/ado/12`). Une famille n’atteint pas les données d’une autre (instance mono-famille,
et `FamilyScope` répond 404), mais les identifiants laissent deviner des volumes et des ordres de création.

## Décision

Passer toutes les entités en UUID v7 (`Uuid::v7()`, `UuidType`, `uuid` natif PostgreSQL) dans une version à
part, et non en même temps que le passage au cookie de session, parce que la migration est large et risquée
pour les installations en service :

- une migration de données qui ajoute une colonne UUID à chaque table, la remplit, recâble toutes les clés
  étrangères puis remplace les clés primaires, testée sur une copie d’une vraie base ;
- les routes valident `Requirement::UUID_V7` au lieu de `Requirement::DIGITS` ;
- le frontend passe de `number` à `string` pour tous les identifiants (`core/api/models.ts`, formulaires,
  routes) ;
- les tests (`ApiTestCase`, `firstAccountId()`…) suivent.

## Conséquences

- En attendant, l’écart est connu et documenté ici ; les Voters et `FamilyScope` restent le vrai contrôle
  d’accès, avec ou sans UUID.
